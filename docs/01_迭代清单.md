### v1.7.6 · 「动画时间不长」根治 —— 姿态轮换（2026-10-04 接手后）

**用户反馈**：「有点动画了好像，但是时间并不长」。给诊断加了**占空比**指标后定位到根因。

**新增诊断能力：占空比**
- `Soullink 幅度(N帧)` 现在同时报 **激活%**（|v|>0.1 的帧占比）与 **运动%**（逐帧变化 >0.002 的占比）
- 统计窗口 300 帧（5s）→ **600 帧（10s）** —— 「动画时长」是统计问题，窗口太短看不出占空比
- 让「有没有动画」从主观判断变成**可量化**

**首轮实测（v1.7.5 状态）**

| 参数 | 激活% | 运动% | 判断 |
|---|---|---|---|
| `AngleX/Y/Z`、`Breath` | 88~100% | **62~93%** | ✅ 连续微动一直在动 |
| `132` 前倾 | **74~100%** | 5% | ❌ **几乎常开** —— 一直微微前倾，不构成「动作」 |
| `135` 比心 | 28~68% | 3~9% | ⚠️ 偏高 |
| `131`/`136` QQ人 | 17~28% | 5~8% | ⚠️ 偏低 |
| `125`/`130`/`133`/`134` | **0%** | 0% | ❌ 从未出现 |

**根因（关键认知）**
> `privateEmotionMap` 是 **VAD 连续驱动**的，**没有「播放一次」的语义** ——
> 只要 VAD 落在窗口内姿态就**常开**，VAD 一离开就**消失**。
> 同组内 `amount + priority/100` 高者恒胜 → **强者恒强**：
> 要么某个姿态霸占整组（前倾 100%），要么某些永远排不上（4 个恒 0%）。

**修复：按 arousal 把同组姿态切成不重叠的三段，强制轮换**

| 组 | 低段 | 中段 | 高段 |
|---|---|---|---|
| `miku_pose` | `spin` 圈圈 A[0.24,0.36] | `qqMode` QQ人 A[0.34,0.44] | `leanForward` 前倾 A[0.42,0.60] + V≥0.70 |
| `miku_prop` | `scallion` 大葱 A[0.24,0.34] | `heart` 比心 A[0.28,0.40] | `sing` 唱歌 A[0.38,0.48] |

配套：`decayRate` 0.18→**0.26**（0.18 时情绪会累积、VAD 漂高导致前倾常开）；
`spontaneity`→2.0、`avoidRepeatWindow` 4→**2**（更快轮换）；姿态 `intensity`→0.95。

**结果（真机实测，5 个 10 秒窗口）**

| 姿态 | 修复前 | 修复后 |
|---|---|---|
| `125` 圈圈 | 0% | 28 / 0 / 21 / 12 / 0 % |
| `130` 脸红 | 0% | 58 / 0 / 29 / 27 / 7 % |
| `131` QQ人 | 0% | 0 / **65** / 50 / 22 / 4 % |
| `132` 前倾 | 74~100% 常开 | 75 / 36 / 35 / 73 / 99 %（仍偏高，见下） |
| `133` 大葱 | 0% | 28 / 0 / 0 / 0 / 0 % |
| `134` 唱歌 | 0% | 0 / **46** / 22 / 20 / 4 % |
| `135` 比心 | 0% | 0 / 22 / **50** / 13 / 0 % |
| `136` QQ人 | 0% | 0 / **65** / 50 / 22 / 4 % |

→ **7/7 姿态全部能出现并轮换**（此前 4 个恒 0%）；头部运动占比维持 62~93%。

**遗留**
- `132` 前倾在 V 高时仍会较长时间占据（最后一个窗口 99%）。
  已把 V 门槛提到 0.70 收窄，但**这是引擎「VAD 连续驱动」的设计特性**，
  调参只能缓解、不能根除。若要真正的「播一段动作就结束」，
  需要走 `SpeechPerformancePlanner`（有时长语义）或给引擎提需求。

**变更**
- `versionCode` 13 → 14，`versionName` 1.7.5 → 1.7.6

### v1.7.5 · 「没有动画感」根治（2026-10-04 接手后）

**用户反馈**：「没有动画的感觉呢」。复盘后确认是**三个叠加的根因**，逐一用数据定位并修复：

**根因 1 · 幅度只有满量程的 3~12%**
- 实测 `ParamAngleX` 只摆 **0.78~3.51**，而 Cubism 满量程是 ±30 → 头部转 2 度，人眼看不出
- 对比：内置 idle 是 `sin(t*0.65)*5.5 + sin(t*0.19)*2.0`（±7.5）—— **我关掉了它，换上一个幅度只有 1/3 的引擎**
- 修复：放大 `parameterMap` 的 `scale` —— head 30→**60**、body 12→**28**、gaze 1→**2.5**
- 光调 `motionStyle` 救不了：增益上限只有 **2×**（见 `MotionStyle.ts` 的 clamp）

**根因 2 · 没有情绪底色，VAD 死贴 0**
- 引擎默认 `baseline=(0,0,0)`、`ambientDriftStrength=0.034` → `情绪=soft-low V=-0.00`
- 后果：`privateEmotionMap` 的高情绪门槛**永远达不到** → 表情层全程不动
- 修复：新增 `profile.emotionPersonality` 支持，设
  `baseline={valence:0.40, arousal:0.35, dominance:0.10}`、`ambientDriftStrength=0.09`（上限）、
  `reactivity=1.6`、`decayRate=0.30`（比默认慢）
- 效果：`情绪=curious V=0.41 A=0.35 D=0.11` —— **VAD 离开 0，有了「活着」的起伏**

**根因 3 · `privateEmotionMap` 压根没生效（最隐蔽）**
- 现象：`snapshot.live2dParams` 只有 **23 个参数**，7 个离散姿态参数**一个都不在里面**
- 根因：引擎的 `deriveParameterRanges()` **只扫 `parameterMap` + `customParams`，
  完全不含 `privateEmotionMap` 的目标** → `Param130/133/134/135/125/131/132/136`
  拿不到 min/max/default → 被 `selectDeclaredCandidates` **直接丢弃**
- 正确做法：由**宿主**调 `runtime.setPrivateVADParameters(info)` 喂模型真实参数表
  （`VADPrivateParameterInfo = {min,max,default}`），引擎自己推不出来
- 实现：`buildPrivateParamInfo()` 用 `core.getParameterIndex(id)` 反查
  （★ pixi-live2d-display **0.4.0 没有 `getParameterId(index)`**，按 index 枚举会抛异常）
- 踩坑：该函数每帧被调，失败日志把环形缓冲**刷爆**（一秒几百条）→ 加了尝试上限（900 次）+ 只记一次

**结果（真机实测）**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `snapshot` 参数种类 | 23 | **30** |
| 私有情绪候选 | **0** | **8/8** |
| `AngleY` 摆幅 | Δ0.62~2.95 | **Δ21.47**（满量程 72%） |
| `AngleZ` 摆幅 | Δ0.23~5.62 | **Δ14.68** |
| `AngleX` 摆幅 | Δ0.78~3.51 | **Δ11.38** |
| 离散姿态 | 全部恒 0 | `131/132/135/136` 间歇 0.70~0.80 |

- 终调：`blush` 的 D 门槛 0.20→**0.06**、`intensity` 0.9→**0.6**
  （0.20 时脸红 0.90 **常开**，反而假）
- 档案已**固化进 assets**（`sdcard` 覆盖已删，assets 为唯一来源）

**新增能力**
- `profile.motionStyle` 可覆盖动作风格（预设 + 全部旋钮）
- `profile.emotionPersonality` 可覆盖情绪底色
- **Soullink 档案支持 sdcard 覆盖**（`/sdcard/Live2DModels/<模型>/soullink.profile.json`）
  —— 调参不用重新构建装机，这是本轮能快速迭代 6 轮的关键
- `Soullink 幅度(N帧)` 诊断日志：统计窗口内各参数的 min/max/**Δ**，让「有没有动画」可量化

**变更**
- `versionCode` 12 → 13，`versionName` 1.7.4 → 1.7.5

### v1.6.0 · 捕获窗口泄漏修复 + 透明度真相（2026-10-02 接手后）

**修复**
- [x] **Bug-016 捕获窗口泄漏**（★ 本项目最隐蔽的资源泄漏）
  - 现象：拖动几次之后拖不动；模型移动时「到处闪/瞬移」
  - 根因：`detachOverlay()` 只移除渲染窗口，**从未调用 `removeTouchCatcher()`**。
    Service 停止后进程通常仍存活（Android 保留缓存进程），窗口不随 token 消失 →
    残留捕获窗口继续可触摸，而它的 `OnTouchListener` 闭包指向**已销毁的旧 Service 实例**
    （`webView` 已为 null）→ 触摸被吞掉却什么都不做。
    Android 在 `ACTION_DOWN` 时绑定整个手势序列，所以撞进残留矩形的手势**整段**失效。
  - 实测：3 轮「停→启」后 `dumpsys` 里累积出 **5 个捕获窗口**（应为 1 个）
  - 修复：`detachOverlay()` 中补 `removeTouchCatcher()`
  - 验证：连续 3 轮启停，捕获窗口 `1 → 0 → 1`，**零泄漏**

**新增约束（架构层，已写入 00_交接总纲 §五 第 6 条）**
- [x] **全屏穿透式悬浮窗的不透明度硬上限为 0.8**
  - 现象：整体透明度拉到 100% 仍然「有点透明」
  - 根因：Android 12+ 对带 `FLAG_NOT_TOUCHABLE` 的系统悬浮窗强制压低 alpha。
    系统原话（`logcat`）：
    `App com.live2d.overlay has a system alert window (type = 2038) with FLAG_NOT_TOUCHABLE
     and LayoutParams.alpha = 1.00 > 0.80, setting alpha to 0.80 to let touches pass through`
  - **推翻了 v1.4.0 的结论**：当时记为「模型自带 alpha 的观感」，属**误判**
  - 已排除的两条修复路径（都实测过）：
    1. 反射 `touchableRegion` / `setTouchableRegion` → **本机不存在该成员**
       （枚举 `WindowManager.LayoutParams` 全部触摸相关成员：只有 5 个 `FLAG_*` 常量，方法为空）
    2. `settings put secure maximum_obscuring_opacity_for_touch 1.0` + **重启** → **仍压制到 0.8**
  - 结论：**0.8 是本机硬上限**。要 100% 只能改用「把模型渲染进可触摸的包围盒窗口」，
    代价是包围盒矩形内的触摸不再穿透到桌面（见 §二 P1-6，**待用户决策**）

### v1.7.0 · 拖动抖动根治 + 动作库外置 + 透明度定案（2026-10-02 接手后）

**修复**
- [x] **Bug-017 拖动时模型闪现跳动的真正根因**（★ Bug-013 只修了一半）
  - 现象：拖动过程中模型到处闪 / 跳动（Bug-016 修完泄漏后**仍然存在**）
  - 根因：`forwardTouchToWebView()` 用 `ev.x + catcherOffsetX` 换算屏幕坐标。
    `ev.x` 是「事件生成那一刻」相对捕获窗口的**局部**坐标，而偏移量是
    `syncTouchCatcher()` **刚发布**的值 —— 但 `updateViewLayout()` 要经 Binder
    **异步生效**。窗口移动后的那几帧里，「新偏移 + 旧局部坐标」算出的坐标会整体
    偏掉一个位移量。
    拖动时捕获窗口**每帧都跟着模型移动**，于是形成自激振荡：
    窗口移动 → 坐标偏掉 → 页面按**增量**（`model.x += x - pointerLastX`）
    又把模型挪一次 → 命中区再移动 → 再偏掉…每一次偏差都**永久留在模型位置上**。
  - 修复：改用 `ev.rawX / ev.rawY`（输入系统给的**屏幕**坐标），与窗口位置和
    我们的记账彻底解耦。同时删除已无用的 `@Volatile catcherOffsetX/Y/ScaleX/Y`。
  - 验证：单指注入拖拽 4 步，命中区 `L = 220 → 185 → 149 → 114`，
    **步长恒为 35~36 px，零跳变**；理论值 `80 × 712/1600 = 35.6`，与手指 1:1 跟手

### v1.7.1 · 双指缩放闪退根治 + 调试通道收口（2026-10-02 接手后）

**修复**
- [x] **Bug-018 双指缩放到下限时闪退**（★ 用户报「缩小到一定程度后就会闪退」）
  - 现象：双指捏合缩小，缩到下限（0.30）时 App 闪退
  - **定位手段**：`logcat -b crash` 已被清空，改从 **Android dropbox** 取证
    （`adb shell dumpsys dropbox --print`）—— 崩溃记录长期保留，不受 logcat 清空影响
  - 崩溃栈（v1.7.0，`2026-10-03 02:00:54`，且 15 秒前还有一次同源 native crash）：
    ```
    java.lang.IllegalArgumentException: invalid pointerIndex 1 for MotionEvent
      { action=POINTER_UP(1), id[0]=0, ... }
        at MotionEvent.getPointerId
        at ViewGroup.dispatchTouchEvent
        at OverlayService.forwardTouchToWebView(OverlayService.kt:681)
    ```
  - 根因：`forwardTouchToWebView()` 用的是**单点**重载
    `MotionEvent.obtain(downTime, eventTime, action, x, y, metaState)`，构造出的
    `pointerCount` 恒为 1；而 `ACTION_POINTER_DOWN/UP` 的 action 里**编码了 pointerIndex**
    → `dispatchTouchEvent` 调 `getPointerId(1)` 越界 → 崩溃。
    之所以能走到这里：`handlePinch()` 只在 `pinchActive && pointerCount <= 2` 时消费
    `ACTION_POINTER_UP`，**其余情况返回 false 让它落到转发路径** —— 任何多点触控都可能触发。
  - 修复（三层）：
    1. `forwardTouchToWebView()` 拒绝 `pointerCount != 1`，并直接丢弃
       `ACTION_POINTER_DOWN / ACTION_POINTER_UP`
    2. `handlePinch()` 的 POINTER_DOWN / POINTER_UP 分支**始终消费**（`return true`）
    3. 新增 `suppressNextUp`：双指收尾的那个 `ACTION_UP` 也吃掉，
       否则页面把它当一次点击（白播动作 + 特效）
  - 验证：单指拖拽回归 `L=117→77→37`（步长恒为 40 = `90×712/1600`），`crash` 缓冲区为空

**安全**
- [x] **P0-4 `ACTION_DEBUG_JS` 加 debug 守卫** —— 但**不能只加守卫**
  - 发现：`MainActivity.pushPageOption()` 的三个热切换开关（点击特效 / 边缘吸附 / 动作轮播）
    **正借道 `ACTION_DEBUG_JS` 注入整段 JS** —— 直接加守卫会让 release 下开关失效
