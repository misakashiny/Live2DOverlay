│  └──────┬───────┘  └──────┬───────┘  └───────┬───────┘ │
│         │                 │                   │         │
│         └────────┬────────┴───────────────────┘         │

│          EmotionToActionMapper                          │

└────────────────────┬────────────────────────────────────┘
                     │  桥接（Live2DJSBridge）
┌────────────────────▼────────────────────────────────────┐

**为什么加"编排层"**：人设、情绪、对话三者互相依赖（对话内容影响情绪，情绪影响回复语气，人设约束两者），必须有一个统一协调者，不能让 JS 页面直接管理业务状态。

## 二、角色人设 · JSON Schema

### 2.1 设计原则

1. **人设与实现分离**：JSON 只描述"是谁"，不含任何代码逻辑
2. **可组合**：`emotionBias` 微调情绪基线，`actionLibrary` 引用动作库（可复用）
3. **可验证**：用 JSON Schema 约束字段，加载时校验，错误给出明确提示
4. **兼容热更**：人设文件可放 `/sdcard/Live2DModels/<角色>/persona.json`，换角色免改代码

### 2.2 Schema 草案

```jsonc
{
  "$schema": "https://live2d-overlay.local/schema/persona-v1.json",
  "schemaVersion": 1,

  // ── 身份 ──────────────────────────────────────────
  "id": "miku",
  "name": "初音未来",
  "avatar": "miku.model3.json",        // 相对本目录
  "tags": ["元气", "歌姬", "傲娇"],

  // ── 大模型对话配置 ─────────────────────────────────
  "llm": {
    "provider": "openai-compatible",   // 抽象层：openai / anthropic / 自定义
    "model": "gpt-4o-mini",
    "temperature": 0.8,
    "maxTokens": 120,                  // 短回复，适合桌面陪伴场景
    "endpointRef": "default",          // 指向全局密钥库，人设文件不存 key
    "systemPromptTemplate": "system.md" // 外置模板文件，支持变量插值
  },

  // ── 性格（约束 LLM + 影响情绪基线）──────────────────
  "personality": {
    "traits": {
      "cheerfulness": 0.85,            // 0~1，开朗度
      "shyness": 0.40,
      "talkativeness": 0.70,
      "clinginess": 0.60               // 粘人度，影响主动搭话频率
    },
    "speechStyle": {
      "tone": "活泼、口语化、偶尔卖萌",
      "verbosity": "short",            // short / normal / verbose
      "forbidden": ["正式公文腔", "长篇说教"],
      "catchphrases": ["诶嘿~", "才、才不是呢！"]
    }
  },

  // ── 情绪基线偏置（见第三章）────────────────────────
  "emotionBias": {
    "joy":      +0.15,
    "shyness":  +0.05,
    "anger":    -0.20,
    "sadness":  -0.10
  },

  // ── 反应映射：语义标签 → 具体表现 ───────────────────
  "reactions": {
    "onTap": {
      "actions": ["Param134", "Param135"],   // 参数驱动动作
      "effects": ["ripple", "sparkle"],      // 点击特效
      "weighted": true                       // 按权重随机
    },
    "onLongPressDrag": {
      "reaction": "surprise",
      "holdFeedback": "grabPulse"            // 抓住脉冲反馈
    },
    "onIdle": {
      "intervalMs": [8000, 20000],           // 空闲小动作间隔区间
      "actions": ["Param125", "Param130"]
    },
    "onEmotionChange": {
      "joy_high":   { "param": "Param130", "value": 1.0 },  // 脸红
      "anger_high": { "param": "Param132", "value": 1.0 }   // 前倾
    }
  },

  // ── 记忆（可选，轻量上下文）────────────────────────
  "memory": {
    "maxTurns": 20,                    // 保留最近 N 轮对话
    "persist": true                    // 是否落盘到 shared_prefs
  }
}
```

### 2.3 关键设计取舍

| 决策 | 理由 | 代价 |
|---|---|---|
| 人设文件**不存 API Key**，只存 `endpointRef` | 人设文件可能被分享/导出，密钥泄露风险高 | 多一层间接引用 |
| `systemPromptTemplate` 用**外置 .md + 变量插值** | 长 prompt 写在 JSON 里转义痛苦、难维护 | 需实现简单模板引擎 |
| `emotionBias` 作为**偏置**而非绝对值 | 偏置可与动态情绪叠加，同一套情绪引擎适配不同角色 | 需明确叠加/裁剪规则 |
| `endpointRef` 而非硬编码 provider | 便于切换本地/云、多账号 | 需密钥管理模块 |

## 三、情绪系统 · 架构推演

### 3.1 情绪模型：连续值 + 触发阈值

**不用离散状态机，用连续标量**——因为情绪是渐变的，且需要"累积"语义。

```
维度集合（6 维，可扩展）：
  joy       喜悦
  anger     愤怒
  sadness   悲伤
  shyness   害羞
  surprise  惊讶
  calm      平静

每维取值 0.0 ~ 1.0
```

### 3.2 三条驱动源

```
┌──────────────────────────────────────────────────────┐
│                    EmotionEngine                      │
│                                                       │
│  ① 事件注入        ② AI 推断         ③ 自然衰减        │
│  ┌──────────┐     ┌──────────┐      ┌──────────┐   │
│  │ 触摸/点击 │     │ LLM 返回  │      │ 每 tick   │   │
│  │ 拖拽/空闲 │     │ 情绪标签  │      │ 回归基线   │   │
│  └────┬─────┘     └────┬─────┘      └────┬─────┘   │
│       └────────────────┼─────────────────┘           │
│                        ▼                              │
│              value = clamp(base + Σdelta, 0, 1)       │
│                        │                              │
│                        ▼                              │
│              触发阈值检查 → 发事件                       │
└────────────────────────┬─────────────────────────────┘
                         ▼
              EmotionToActionMapper
                         ▼
              参数驱动动作 / 表情 / 特效
```

**三个驱动源的设计意图**：

- **事件注入（本地、即时）**：点击 → joy +0.1，拖拽 → surprise +0.3。零延迟，保证反馈手感。
- **AI 推断（联网、异步）**：LLM 在回复时附带情绪标签（见 3.4）。有网络延迟，因此**异步到达、事后叠加**，不阻塞动画。
- **自然衰减（每帧/每秒）**：所有维度以 `decayRate` 向 `baseline + emotionBias` 回归。这是"情绪会平复"的来源。

### 3.3 累积与触发

```kotlin
// 伪代码
fun tick(dtMs: Long) {
    for (dim in Dimension.values()) {
        val target = baseline[dim] + bias[dim]
        val cur = value[dim]
        val rate = decayRate[dim] * dtMs / 1000f
        value[dim] = cur + (target - cur) * rate.coerceAtMost(1f)
    }
    checkTriggers()
}

fun checkTriggers() {
    // 进入"兴奋"需要 joy 连续高于阈值
    if (value[JOY] >= 0.75 && !flags.excited) {
        flags.excited = true
        emit(EmotionEvent.Enter("excited"))
    }
    // 情绪累积到上限触发特殊表现
    if (value[JOY] >= 0.95) {
        emit(EmotionEvent.Peak("joy"))   // → 触发稀有动作
    }
}
```

**"累积触发"的语义**：不是单次事件就到达阈值，而是**多次小事件叠加 + 衰减慢于累积**，营造"越来越开心"的观感。

### 3.4 LLM 输出契约

要求模型返回**结构化 JSON**（用 function calling / response_format 约束），而非自然语言里猜情绪：

```json
{
  "reply": "诶嘿~ 今天也来陪我了吗？",
  "emotion": {
    "joy": 0.8,
    "shyness": 0.3
  },
  "intent": "greet",
  "actionHint": "Param134"
}
```

**降级策略**（网络失败/格式错误时）：
1. 有 `reply` 无 `emotion` → 只显示回复，情绪不动
2. 完全失败 → 走本地规则库的兜底回复 + 事件注入驱动情绪
3. 超时（建议 8s）→ 静默失败，不打断用户

## 四、接口契约

### 4.1 Kotlin → JS

```javascript
// 推送情绪状态（渲染层据此选动作）
window.__mikuLive2DApplyEmotion(json)
//   json: { joy: 0.8, anger: 0.1, ..., dominant: "joy" }

// 播放指定动作（绕过情绪直接播）
window.__mikuLive2DPlayAction(paramName)

// 播放点击特效
window.__mikuLive2DPlayEffect(effectName, x, y)
```

### 4.2 JS → Kotlin

```kotlin
// 用户交互事件上报（供情绪引擎消费）
@JavascriptInterface fun onUserEvent(type: String, payload: String)
//   type: "tap" | "drag_start" | "drag_end" | "idle"

// 请求对话
@JavascriptInterface fun requestDialogue(userText: String)
```

## 五、实现顺序建议（分四阶段）

| 阶段 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **P1** | 人设 JSON 加载 + 校验 + 多角色切换（**纯本地**） | 无 | 低 |
| **P2** | 情绪引擎（事件注入 + 衰减 + 触发）**纯本地** | P1 | 中（调参） |
| **P3** | 情绪 → 动作映射 + 点击特效 | P2 | 低 |
| **P4** | 接入 LLM 对话（含结构化输出与降级） | P1 | **高**（网络/成本/密钥） |

**为什么把 LLM 放最后**：P1–P3 完全不依赖网络，能先交付一个"有情绪、会反应"的角色。LLM 是增强项，不是地基。这样即使 API 不可用，核心体验仍成立。

## 六、风险与开放问题

### 已识别风险

1. **API Key 安全**：明文存 SharedPreferences 会被 root 设备读取。需 `EncryptedSharedPreferences`。
2. **网络延迟破坏沉浸感**：桌面陪伴场景对延迟敏感。**对策**：先播"思考中"本地动作，回复到达后再切情绪。
3. **Token 成本**：若支持主动搭话，需限流（如最小间隔 5 分钟）。
4. **情绪抖振**：多个驱动源叠加可能导致情绪值剧烈跳动。**对策**：所有写入走 `clamp` + 变化率限制（每秒最大变化 0.3）。
5. **模型无 Motions 段**（`miku.model3.json` 的已知限制）：情绪映射只能走**参数驱动**，动作表现力受限于已逆向的参数集。

### 待你决策的开放问题

1. **对话触发方式**：只在用户主动点击时对话？还是允许角色主动搭话（需定时器 + 限流）？
2. **是否需要语音**：TTS 会让"陪伴感"强很多，但引入新依赖和成本。
3. **多人设是否共享记忆**：切换角色后，之前的对话历史保留还是清空？
4. **情绪是否需要持久化**：App 重启后情绪归零，还是延续上次状态？
