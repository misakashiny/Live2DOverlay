# AI 驱动情绪系统 · 框架推演（仅设计稿，暂不实现）

> ## ⚠️ v1.7.3 后记：本文的部分设计已被第三方引擎取代
>
> 本项目后来决定接入现成的 [Soullink Emotion SDK](https://github.com/nanlingyin/soullink-emotion-sdk)，
> 它已经把这篇文章里的核心设计**做得更专业**。**读本文前请先看**
> [`33_Soullink引擎接入_决策与实施.md`](33_Soullink引擎接入_决策与实施.md)。
>
> | 本文的设计 | 现状 |
> |---|---|
> | 6 维离散情绪（joy/anger/sadness/shyness/surprise/calm） | ❌ **被 VAD 三轴连续情绪取代**（语义重叠、无法表达强度） |
> | `emotionBias` / `emotionPhysics`（衰减、限速） | ⚠️ 由 Soullink 的 `motionStyle` / `personality` 承载 |
> | 「情绪 → 动作映射」自建映射表 | ❌ **被 `privateEmotionMap` 取代**（自带 VAD 窗口/优先级/排他组） |
> | `EmotionArbiter`（乱序保护 + 权重融合 + 变化率限制） | ⚠️ Soullink 内部已有等价机制 |
> | `DialogueClient` + `ApiKeyStore`（P4） | ⭕ **仍未实现**，对应 Soullink 的 `planner-openai` / `classifier-embedding` |
> | **「AI 提供语义，本地提供物理」的分工原则** | ✅ **依然成立**，且 Soullink 也是这么做的 |
>
> **本文仍有价值的部分**：§一 的分工原则、§4.4 的降级策略、§五 的时序与仲裁思路 ——
> 这些是接第三方引擎时同样要面对的工程问题。

> **状态**：纯设计稿。本文只推演架构、数据结构、接口契约与时序，**不含可运行代码**。
> **关系**：本文是 [`30_AI角色系统_架构推演.md`](30_AI角色系统_架构推演.md) 的**修订与聚焦版**。
> `30` 把情绪设计成「本地事件注入为主 + AI 推断为辅」；本文按最新意图改为
> **「AI 联网推断为主驱动源」**，并明确哪些部分必须留在本地。两文冲突时以本文为准。
>
> **结论先行**：AI 驱动情绪**可行**，但必须保留一条**本地骨架**——
> 情绪值由 AI 决定「往哪走」，本地决定「走多快、怎么衰减、怎么触发」。
> 否则一次网络抖动就会让角色表情卡死。

## 一、与 docs/30 的差异（先看这张表）

| 维度 | `30` 的设计 | 本文的设计 | 为什么改 |
|---|---|---|---|
| 情绪主驱动源 | 本地事件注入（点击/拖拽）为主 | **AI 联网推断为主**，本地事件为辅 | 用户明确要求「情绪由 AI 驱动，通过联网 api」 |
| 事件注入的角色 | 独立驱动源 | **降级为「即时反馈层」**，只做零延迟的手感 | 本地事件无法表达「因为你说的话而害羞」 |
| 衰减 | 每 tick 回归基线 | **不变，仍必须本地** | 网络不可用时情绪不能僵在峰值 |
| 触发阈值 | 本地 `checkTriggers()` | **不变，仍必须本地** | 触发要逐帧判断，不可能走网络 |
| 表情/动作选择 | 本地映射表 | **本地映射表 + AI 给的 `actionHint` 优先** | AI 知道语境，本地知道模型有哪些动作 |
| 联网依赖 | 仅 P4 阶段 | **P2 起就需要** | 情绪本身就是 AI 驱动的 |

> **一句话**：AI 提供**语义**（现在该是什么情绪、为什么），本地提供**物理**
> （数值怎么演化、何时触发、动作怎么落地）。这个分工不能颠倒。

## 二、总体分层

```
┌───────────────────────────────────────────────────────────┐
│ UI 层（MainActivity）                                      │
│  角色选择 · 人设编辑 · 情绪面板（调试用）· 对话入口          │
└───────────────────────┬───────────────────────────────────┘
                        │
┌───────────────────────▼───────────────────────────────────┐
│ 编排层 Orchestrator ★ 核心                                 │
│                                                           │
│  ┌──────────────┐   ┌────────────────┐   ┌─────────────┐ │
│  │ PersonaStore │   │ EmotionEngine  │   │DialogueClient│ │
│  │ 人设加载/切换 │   │ 情绪值 + 衰减   │   │ LLM 调用     │ │
│  └──────┬───────┘   └───────┬────────┘   └──────┬──────┘ │
│         │                   │                    │        │
│         │            ┌──────▼─────────┐          │        │
│         │            │ 情绪驱动仲裁器  │◄─────────┘        │
│         │            │  AI 意图 vs 本地│  AI 返回结构化情绪 │
│         │            │  即时事件 加权  │                   │
│         │            └──────┬─────────┘                   │
│         └───────────┬───────┘                             │
│                     ▼                                     │
│          EmotionToActionMapper                            │
│          （情绪状态 → 动作/表情/参数，复用 MODEL_ACTIONS）  │
└───────────────────────┬───────────────────────────────────┘
                        │ 桥接（Live2DJSBridge）
┌───────────────────────▼───────────────────────────────────┐
│ 渲染层（live2d_decor.html + Pixi + Cubism）                │
│  参数驱动动作 · 表情切换 · 视线跟随 · 点击特效               │
└───────────────────────────────────────────────────────────┘
```

**为什么必须有「仲裁器」**：AI 的返回是**异步、有延迟、可能乱序**的；
本地事件是**同步、零延迟**的。两者都会写情绪值，若直接相加会出现
「用户点了 3 下（本地 joy 已经很高），AI 200ms 后返回一个低 joy 覆盖掉」。
仲裁器负责：**按时间戳排序、按权重融合、限速**（见 §五）。

## 三、角色人设 · JSON 模板（支持多角色切换）

### 3.1 设计原则

1. **人设与实现分离** —— JSON 只描述「是谁」，不含任何逻辑
2. **人设不存 API Key** —— 只存 `endpointRef`，Key 单独走 `ApiKeyStore`
3. **可热更** —— 放 `/sdcard/Live2DModels/<角色>/persona.json`，换角色免改代码
4. **可校验** —— 加载时按 JSON Schema 校验，错误要给人话提示

### 3.2 模板草案

```jsonc
{
  "schemaVersion": 1,

  // ── 身份 ─────────────────────────────────────────────
  "id": "miku",
  "name": "初音未来",
  "avatar": "miku.model3.json",          // 相对本目录
  "tags": ["元气", "歌姬"],

  // ── 大模型配置 ────────────────────────────────────────
  "llm": {
    "endpointRef": "default",            // 指向 ApiKeyStore，人设内不存 Key
    "model": "gpt-4o-mini",
    "temperature": 0.8,
    "maxTokens": 120,                    // 桌面陪伴场景要短回复
    "systemPromptTemplate": "system.md", // 外置模板，支持变量插值
    "emotionSchema": "emotion-v1"        // 约定 AI 必须返回的情绪结构版本
  },

  // ── 性格（约束 LLM + 影响情绪基线）──────────────────────
  "personality": {
    "traits": {
      "cheerfulness": 0.85,              // 0~1
      "shyness": 0.40,
      "talkativeness": 0.70,
      "clinginess": 0.60                 // 粘人度 → 主动搭话频率
    },
    "speechStyle": {
      "tone": "活泼、口语化、偶尔卖萌",
      "verbosity": "short",
      "forbidden": ["正式公文腔", "长篇说教"],
      "catchphrases": ["诶嘿~", "才、才不是呢！"]
    }
  },

  // ── 情绪基线偏置（偏置，不是绝对值）──────────────────────
  "emotionBias": {
    "joy":     +0.15,
    "shyness": +0.05,
    "anger":   -0.20,
    "sadness": -0.10
  },

  // ── 情绪物理参数（本地用，AI 不感知）────────────────────
  "emotionPhysics": {
    "decayRatePerSec": {                 // 每秒回归基线的比例
      "joy": 0.05, "anger": 0.12, "sadness": 0.04,
      "shyness": 0.08, "surprise": 0.25, "calm": 0.06
    },
    "maxDeltaPerSec": 0.30,              // 变化率上限，防抖振
    "aiWeight": 0.70,                    // AI 推断权重
    "localWeight": 0.30                  // 本地事件权重
  },

  // ── 本地即时反馈（零延迟手感，AI 未返回时先用它）──────────
  "localReactions": {
    "onTap":            { "joy": +0.08, "surprise": +0.05 },
    "onLongPressDrag":  { "surprise": +0.20, "shyness": +0.05 },
    "onIdle":           { "calm": +0.02 }
  },

  // ── 情绪 → 表现（本地映射，AI 可用 actionHint 覆盖）───────
  "reactions": {
    "onTap": { "actions": ["Param134", "Param135"], "effects": ["ripple", "sparkle"], "weighted": true },
    "onIdle": { "intervalMs": [8000, 20000], "actions": ["Param125", "Param130"] },
    "onEmotionChange": {
      "joy_high":     { "param": "Param130", "value": 1.0 },  // 脸红
      "anger_high":   { "param": "Param132", "value": 1.0 },  // 前倾
      "surprise_high":{ "param": "Param136", "value": 1.0 }
    }
  },

  // ── 记忆（轻量上下文）───────────────────────────────────
  "memory": { "maxTurns": 20, "persist": true }
}
```

### 3.3 多角色切换

| 项 | 设计 |
|---|---|
| 存储 | `assets/personas/<id>/persona.json`（内置） + `/sdcard/Live2DModels/<id>/persona.json`（热更，优先） |
| 切换粒度 | 人设 + 模型 + 动作库**一起换**（一个角色 = 一个目录） |
| 切换时清什么 | 情绪值重置为 `baseline + bias`；对话历史按 `memory.persist` 决定保留/清空（**待决策**） |
| 配置落点 | `OverlayConfig` 新增 `activePersonaId` |

## 四、AI 驱动情绪 · 核心设计

### 4.1 情绪模型：6 维连续值

```
joy 喜悦 / anger 愤怒 / sadness 悲伤 / shyness 害羞 / surprise 惊讶 / calm 平静
每维 0.0 ~ 1.0
```

用连续标量而非离散状态机，因为情绪是渐变的，且需要「累积」语义
（多次小事件叠加 → 「越来越开心」的观感）。

### 4.2 三条驱动源（重新配比）

```
┌────────────────────────────────────────────────────────────┐
│                     EmotionEngine                          │
│                                                            │
│  ① AI 推断（主）        ② 本地事件（辅）      ③ 自然衰减     │
│  ┌──────────────┐      ┌──────────────┐    ┌────────────┐ │
│  │ LLM 结构化返回 │      │ 点击/拖拽/空闲 │    │ 每 tick     │ │
│  │ 权重 0.70     │      │ 权重 0.30     │    │ 回归基线     │ │
│  │ 异步·有延迟    │      │ 同步·零延迟    │    │ 永远本地     │ │
│  └──────┬───────┘      └──────┬───────┘    └─────┬──────┘ │
│         └──────────────────────┼──────────────────┘        │
│                                ▼                           │
│              value = clamp(base + Σ(w·delta), 0, 1)        │
│              再过一道「变化率限制」（maxDeltaPerSec）        │
│                                ▼                           │
│                    触发阈值检查 → 发事件                     │
└───────────────────────────┬────────────────────────────────┘
                            ▼
              EmotionToActionMapper → 参数驱动动作 / 表情 / 特效
```

**为什么 AI 只能当「主驱动源」而不是「唯一驱动源」**：

| 场景 | 只有 AI | 保留本地 |
|---|---|---|
| 网络 3 秒不可用 | 情绪僵在峰值，表情不动 | 衰减照常，情绪自然回落 ✅ |
| 用户连点 5 下 | 要等 5 次往返 | 立刻有反馈，AI 结果事后融合 ✅ |
| 阈值触发 | 无法逐帧判断 | 本地逐帧判断 ✅ |
| 「因为你说的话而害羞」 | 做不到 | AI 做得到 ✅ |

### 4.3 LLM 输出契约（关键）

**必须让模型返回结构化 JSON**，用 function calling 或 `response_format` 约束，
**不要在自然语言里猜情绪**。

```json
{
  "reply": "诶嘿~ 今天也来陪我了吗？",
  "emotion": { "joy": 0.80, "shyness": 0.30 },
  "intent": "greet",
  "actionHint": "Param134",
  "confidence": 0.9
}
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `reply` | ✅ | 给用户看的话，受 `maxTokens` 与 `verbosity` 约束 |
| `emotion` | ⭕ | **只给变化量或目标值，不给全 6 维** —— 让本地按偏置补全，减少 token |
| `intent` | ⭕ | `greet / comfort / tease / idle_chat…`，用于埋点与限流 |
| `actionHint` | ⭕ | 直接指定动作参数名；**必须校验它在 `MODEL_ACTIONS` 里存在**，否则忽略 |
| `confidence` | ⭕ | 低置信时降低 AI 权重，让本地事件说话 |

> ★ **`actionHint` 必须白名单校验**：模型可能编出不存在的 `Param`，
> 直接 `setParam` 会静默无效或产生怪异姿态。

### 4.4 降级策略（四层，缺一不可）

| 情况 | 行为 |
|---|---|
| 有 `reply` 无 `emotion` | 只显示回复，情绪不动 |
| JSON 解析失败 | 记 `AI` 模块日志，丢弃本次情绪，重试 1 次 |
| 超时（建议 8s） | 静默失败，不打断用户；情绪由本地事件驱动 |
| 完全不可用 | 走本地规则库兜底回复 + 本地事件驱动情绪 |

> ★ **超时期间先播「思考中」本地动作**，否则 8 秒静止会严重破坏沉浸感。

## 五、时序与仲裁（最容易出错的地方）

### 5.1 一次对话的完整时序

```
用户输入/事件
   │
   ├─► ① 本地即时反馈（0ms）
   │      localReactions 直接写情绪 → 立即可见的表情变化
   │
   ├─► ② 播放「思考中」本地动作（0ms）
   │
   ├─► ③ 发请求到 LLM ────────────────► 网络（200ms ~ 8s）
   │                                        │
   │                                        ▼
   │                              ④ 结构化返回，带 requestSeq
   │                                        │
   └────────────────────────────────────────┤
                                            ▼
                            ⑤ 仲裁器：requestSeq 必须 > 已应用的最大值
                               （丢弃乱序到达的旧响应）
                                            ▼
                            ⑥ 按 aiWeight 融合进情绪值
                                            ▼
                            ⑦ EmotionToActionMapper → 动作/表情
```

### 5.2 三条硬约束

1. **乱序保护**：每次请求带自增 `requestSeq`，仲裁器只应用比已处理值更大的响应。
   否则「先问后答」的两次请求会让情绪跳回去。
2. **变化率限制**：所有写入统一走
   `value = clamp(value, prev - maxDelta, prev + maxDelta)`，
   防止多驱动源叠加导致情绪抖振。
3. **不阻塞渲染**：网络调用**绝不能**在渲染 ticker 或主线程里做。
   `DialogueClient` 走独立协程/线程池，结果经 `mainHandler.post` 回主线程再写状态。

## 六、接口契约

### 6.1 Kotlin → JS

```javascript
// 推送情绪状态（渲染层据此选动作/表情）
window.__mikuLive2DApplyEmotion(json)
//   json: { joy: 0.8, anger: 0.1, ..., dominant: "joy", intensity: 0.8 }

// 直接播放指定动作（绕过情绪，AI 的 actionHint 走这里）
window.__mikuLive2DPlayAction(paramName)

// 播放点击特效
window.__mikuLive2DPlayEffect(effectName, x, y)

// 对话气泡（新增，用于显示 reply）
window.__mikuLive2DShowBubble(text, durationMs)
```

### 6.2 JS → Kotlin

```kotlin
// 用户交互事件上报（供本地即时反馈 + 触发对话）
@JavascriptInterface fun onUserEvent(type: String, payload: String)
//   type: "tap" | "drag_start" | "drag_end" | "idle"

// 请求对话
@JavascriptInterface fun requestDialogue(userText: String)
```

## 七、实现顺序（分四阶段）

| 阶段 | 内容 | 需联网 | 依赖 | 风险 |
|---|---|---|---|---|
| **P1** | 人设 JSON 加载 + 校验 + **多角色切换** | 否 | 无 | 低 |
| **P2** | 情绪引擎 + 仲裁器（本地事件 + 衰减 + 触发，**AI 接口留桩**） | 否 | P1 | 中（调参） |
| **P3** | 情绪 → 动作映射 + 点击特效联动 | 否 | P2 | 低 |
| **P4** | **接入 LLM 驱动情绪**（结构化输出 + 四层降级） | **是** | P1 | **高**（网络/成本/密钥） |

> ★ **P1–P3 完全本地可交付**，此时角色已经「有情绪、会反应」，
> 只是情绪来自本地事件而非 AI。P4 把 `EmotionArbiter` 的 AI 权重从 0 打开即可 ——
> **这样设计的好处是：AI 接不上时，产品仍然是完整的。**
> 这与 `30` 的结论一致，但本文把它做成了**同一个引擎的开关**，而不是两套逻辑。

## 八、风险与待决策

### 已识别风险

| # | 风险 | 对策 |
|---|---|---|
| 1 | **API Key 明文存储** —— root 设备可读 | `EncryptedSharedPreferences` |
| 2 | **网络延迟破坏沉浸感** | 先播「思考中」本地动作；回复到达再切情绪 |
| 3 | **Token 成本** —— 主动搭话会失控 | 最小间隔限流（建议 ≥5 分钟）+ 单日上限 |
| 4 | **情绪抖振** —— 多驱动源叠加 | 变化率限制 `maxDeltaPerSec`（§5.2） |
| 5 | **`actionHint` 幻觉** —— 模型编出不存在的参数 | 白名单校验 `MODEL_ACTIONS` |
| 6 | **模型无 `Motions` 段**（`miku.model3.json` 已知限制） | 情绪映射只能走**参数驱动**，表现力受已逆向参数集限制 |
| 7 | **AI 返回的情绪与本地事件打架** | 仲裁器权重 + 乱序保护（§五） |

### 需要你决策的开放问题

1. **对话触发方式**：只在用户主动点击时对话？还是允许角色**主动搭话**（需定时器 + 限流）？
2. **是否需要语音**：TTS 会显著增强陪伴感，但引入新依赖与成本。
3. **多人设是否共享记忆**：切换角色后，对话历史保留还是清空？
4. **情绪是否持久化**：App 重启后情绪归零，还是延续上次状态？
5. **AI 驱动情绪的粒度**：每轮对话推断一次？还是固定间隔（如 30s）也做一次「情绪巡检」？
6. **离线降级的可见性**：网络不可用时，是否要告诉用户「现在是本地模式」？
